# 术语搜索与翻译性能优化设计

## 目标

在不改变现有入口、词库内容、匹配优先级、翻译结果结构、API 配置格式和快捷键的前提下，降低术语搜索和翻译的等待感，并保留旧逻辑作为异常回退。

## 现状与边界

- 术语词库约 796 条。当前主窗口每次输入变化都会同步扫描全部词条、重复规范化字符串并排序。
- 快捷窗口有 150ms/300ms 防抖，但首次查询可能等待词库动态 chunk 加载。
- 未命中本地学习词典的单词会先扫描拼写建议，再检查翻译缓存并请求 API。
- 句子翻译已有 SSE 接收能力，但快捷窗口没有传入增量回调，因此要等完整请求结束才显示。
- 当前实际配置为单一主模型；备用模型链路保留原顺序和语义，不在本次默认路径中改变。

## 方案

1. 抽出纯函数术语索引。词条仍保留原对象引用，预计算缩写、全称、定义的小写文本；搜索只替换重复字符串处理，不改变现有分数和排序规则。索引构建失败时继续使用现有全量扫描。
2. 词库加载完成后后台建立索引；主窗口搜索增加短防抖，回车和快捷窗口的显式查找仍立即执行。
3. 单词翻译先查现有缓存，再执行拼写建议；缓存命中直接返回，未命中才执行建议和 API 请求。
4. 快捷窗口把句子翻译的累计片段传给现有结果状态，最终仍以 `translateQuery` 返回值为准；网络错误、过期请求和空片段继续走现有守卫。
5. 不修改发音请求、窗口动画、API 配置保存格式和备用模型顺序。

## 验收标准

- 术语搜索的精确、前缀、包含、中文、后缀和命令组合结果顺序与现有实现一致。
- 空输入、词库未加载、用户词条变更时仍能得到现有结果。
- 翻译缓存命中不再执行拼写建议扫描；缓存未命中仍保留建议和 API 请求。
- 快捷窗口句子翻译能显示累计片段，最终结果与请求完成后的文本一致。
- Node 回归测试通过，`npm run build` 通过。
- 构建产物部署到 `D:\EmbedQuickRef`，不覆盖用户数据文件。
